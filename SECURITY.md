# Security

GITVerse by PRAPAWITY is experimental. Use the latest published release; no older release line currently receives security backports.

## Reporting a vulnerability

Do not post exploit details, credentials, or private repository data in public issues.

Use the repository's [private vulnerability reporting page](https://github.com/prapawity/GITVerse-by-PRAPAWITY/security/advisories/new) when enabled. The maintainer must enable private vulnerability reporting in GitHub repository settings before public launch. If the private form is unavailable, open a public issue requesting a private contact channel without disclosing vulnerability details.

Include affected versions, operating system, impact, and minimal reproduction steps using a disposable repository. Remove secrets and personal information.

## Trust boundaries

The CI dependency-security job runs `npm run security:audit` against the public npm registry and fails on high/critical advisories, including build tools; this check is not marked as allowed-to-fail. The current lockfile passes a clean-install audit after upgrading Electron/Vite and overriding vulnerable nested Zod/minimatch versions. Review and remove overrides when upstream ranges include the fixes. Dependabot proposes weekly dependency and GitHub Actions updates against `develop`. These checks detect known dependency advisories, not all source vulnerabilities or leaked secrets; a clean result can change as new advisories are published.

- Git operations and the integrated terminal execute with the user's OS permissions. Only open repositories you trust; Git hooks and local configuration can execute programs.
- The app window shows untrusted content (Markdown from repositories, pull requests, issues and AI output) and holds a bridge to Git, files and the terminal, so it is isolated from the web. Links open in the system browser (HTTPS only); new windows, navigation or redirects away from the bundled app, and embedded webviews are blocked. Electron runs the window sandboxed with context isolation, and every IPC handler rejects calls that do not come from the app's own top-level page. Both builds ship a Content-Security-Policy that allows only the bundled scripts and no frames or plugins (the Electron dev server runs without it for hot reload).
- Values the window passes to Git are checked in both backends: hashes, refs, branch and tag names, and worktree paths that could start with `-` are refused, so they cannot be read as Git options (for example `--output=<file>`). Working-tree file reads, writes, previews and removals resolve symlinked parent folders and stay inside the repository.
- Clone accepts only HTTPS or SSH URLs without embedded credentials, refuses Git's `<transport>::<address>` remote-helper syntax, and restricts Git to the `https` and `ssh` protocols for that clone. Submodule updates rely on Git's own protocol policy for repository-supplied URLs.
- The integrated terminal starts in an existing absolute folder (otherwise the home folder). A custom shell must be an absolute path to a known shell or one listed in `/etc/shells`; otherwise the system default shell is used. The terminal inherits the app's environment.
- Agent Sessions start only agents from a fixed list, each on its own branch in a worktree created directly inside `<repo>.agents/`. On macOS and Linux the task is passed as a single-quoted argument; on Windows a task containing characters cmd or PowerShell would expand (`"`, `%`, `!`, `$`, backtick, line breaks) is copied to the clipboard to paste instead of being typed into the terminal. Agents run with the user's permissions in that worktree, and saved setup commands run in it too.
- Hosting credentials are never sourced from push profiles. The app checks saved hosting, Git, CLI, and configured environment credentials only after the user explicitly chooses that action; those credentials are sent to the displayed host for verification. API requests follow redirects only to the same host over HTTPS, so the token is not forwarded elsewhere, and a host name is re-checked before it is passed to `git credential fill`.
- Discard is destructive and requires confirmation. Unstaged changes and untracked files may be permanently lost; staged content is retained. Discard checks current diff snapshots and refuses conflicts, active operations, directories, and whole-submodule removal. Untracked removal is nonrecursive and path-confined; hunk patches are generated from the verified Git diff, not arbitrary renderer-supplied patches. Batch execution is not transactional, and there is no app undo for discard.
- Force push requires explicit confirmation and uses a target-specific `--force-with-lease` with the remote-tracking hash captured when the Push dialog opened, never unconditional `--force`. A changed remote rejects the push; this protects against concurrent updates but does not prevent intentionally replacing remote-only commits already covered by the confirmed lease. Fetch and review remote history before retrying a stale lease. Server-side branch protections are not bypassed.
- AI features can send code and repository metadata to the selected external provider.
- Local macOS installers are ad-hoc signed, not Developer ID signed or notarized; Windows distribution signing is not configured. Electron macOS downloads validate the release asset's SHA-256 digest and size before opening an installer for manual replacement; the digest comes from the same GitHub release, so it detects corruption, not a compromised release. Windows/Linux use electron-updater for installation, while Tauri release updates require bundles signed with the updater key embedded at build time. These checks do not replace trusted distribution, publisher signing, or review of the release workflow.
- Never store secrets in source or commit application user-data files.
